# 文档维护规范

## 单一职责与归属

- 根 `README.md` 为英文项目入口，`README.zh-CN.md` 和 `README.ja.md` 分别提供简体中文和日文版本。三份 README 的项目范围、功能、目录与许可说明应同步维护。
- `docs/` 下的设计、开发与数据来源文档以简体中文为主，由 `docs/README.md` 按领域索引。本地开发与部署说明归 `development/`。
- `docs/roadmap.md` 维护后续功能改进。资料边界与验证方式分别就近记录在领域文档和验证规范中。
- `design/areas/` 描述跨板块关系；`stations/` 负责构内依据；`public-areas/` 负责公共面；`buildings/` 负责造型与接入。
- `development/` 负责开发约定；`docs/data/` 负责来源评估和审计。原始文件、哈希和直接事实登记在 `references/catalog.json`；派生资源及重建命令仍放 `data/`、`scripts/` 的就近 README。

不要为每次提交创建文档或为每个小函数拆文件。已有领域内新增小节即可；复杂到需要独立来源、边界和维护入口时再拆分。

## 设计文档应包含

1. **范围与归属**：说明区域、层级和板块。共用源码入口集中在领域索引，单页可引用解释独有规则所需的模块或数据。
2. **资料事实**：原文件链接、版本或 catalog 条目、页码／对象，以及能直接确认的关系。
3. **当前实现与拟合**：坐标基准、简化方式和人工估计，不能把模型值描述为实测。
4. **未确定项**：区别缺资料、未建模、未核实授权和未做人工验收，并说明现有结论的适用范围。
5. **验证入口**：可重建脚本、相关测试领域，以及检查不能证明的内容。

几何相邻不是入口，图上同层不是实测共面，公开文件不是改编授权。中文说明与源码中的英文注释各自保持一致；界面文案由 i18n 管理，不从文档复制到源码。

## 更新与删除

只更新受影响领域。参数以现役配置为准，文档只保留解释它的依据与约束；失效路径、旧版本 UI 和已完成迁移流水及时删除或概括。少量有核对价值的历次修正可留在所属领域，但必须标明历史语境，不能覆盖当前实现。

不保留独立 `archive/`：旧方案和旧坐标实现通过 Git 历史追溯。删除前检查其中唯一的来源、设计约束和未决项，先并入现行文档，再修正全部引用。原始参考文件不属于文档垃圾，不随文档治理删除。

## 变更日志

- 在根目录 [CHANGELOG.md](../../CHANGELOG.md) 的 `Unreleased` 区记录会影响使用、部署或兼容性的重要变更。用使用者能理解的描述概括影响，相关修复合并在同一条中。
- 按实际变更使用 `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、`Security`，省略空分类。涉及升级操作的变更附简短说明。
- 发布时，将 `Unreleased` 中随本次版本交付的条目移入对应版本，标题写为 `## [版本号] - YYYY-MM-DD`。最新版本排在上方。仓库有可用的公开版本链接后，再为标题补上版本或比较链接。

## 格式与检查

文件名用英文短横线，标题和说明默认中文；使用相对 Markdown 链接。根目录相对源码路径用反引号并说明基准，勿混用退役模块名。目录结构用 tree，说明归属而非穷举所有文件。

移动文档时同步更新根 README、AGENTS、区域索引、源码旁 README、数据及脚本说明和必要的源码注释。检查本地文件及目录链接、残留旧路径、命令路径、`git diff --check`，不把失效链接保留成重定向空壳。本地链接检查与外部来源复核分别记录。
